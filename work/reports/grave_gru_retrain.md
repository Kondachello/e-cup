### Почему это мёртво до обучения (точная алгебра, не формула)

Контаминированная gru_final — с форой 16-дневной утечки — это **верхняя граница**
чистой версии. Замер против нового бленда 1.665647 (margin.py, точная алгебра пары):

```
gru_final   скор 1.697063   корр 0.98097   ЗАПАС +0.00052   вклад 0.000006 = шум
```

Порог принятия 0.0003 при скоре 1.70 требует запаса 0.00412 — в 8 раз выше
верхней границы. Проверка «мёртвые оживают в наборах» (новая реалия #4) сделана
прямо (joint_gain.py, честный полусплит):

```
gru_final соло               −0.000010  (вес 0.012)  шум
kevf_s42 соло                −0.000011  (вес 0.041)  шум   [локальный снапшот шага 1500]
НАБОР gru_final + kevf_s42   −0.000009  (веса 0.016/0.047)  шум
```

Не оживает и в наборе. Оживали разные МЕХАНИЗМЫ (застоялость tfm3_stale28, hazard
hz_v1_pb); ниша «секвенс» в новом бленде уже занята вниманием: gseq_small/gseq_big,
tfm3b_cal + tfm3b_pre2_cal (суммарно ~0.20), tfm3_stale28, kevf на подходе, плюс
fusion_v3* (Conv1d(7,7)+трансформер над теми же дневными тензорами, суммарно ~0.25).
Дневная сетка 112×6 — строгое подмножество seq3 (112×12) и kevf (события, 15
каналов, 364 дня): даже идеальная RNN на ней ограничена представлением.

Рассмотренный и отвергнутый вариант A′ — портировать train_gru на seq3 (тензоры
живы, gap30-чистые): это тот же потолок представления и по сути контрольная рука
fusion_v3 без табличного плеча, ценой тяжёлого слота M1.

## Путь B: GRU-энкодер на событийном хранилище kevf

Литература утверждает класс ЭНКОДЕРА, а не представления. Честная проверка —
поменять только энкодер при том же токене. В `kaggle_seq.py` это флаг
`--encoder gru`: proj → GRU(d, --layers) по хронологии (токены store развёрнуты,
валидность-префикс сохраняется), голова concat(h_N, mean, max) → тот же trunk 3d,
те же 4 головы, потери, калибровка 2-fold, выгрузки val+test с одних весов,
чекпойнты. ALiBi/aux-dt (механизмы внимания) закрыты assert'ом; time2vec,
event-dropout, jitter, mono, swa совместимы. Для GRU добавлен clip_grad_norm 1.0
(канонический AMP-паттерн, у тфм-пути поведение не тронуто).

## ГОТОВЫЙ СПЕК ЗАПУСКА (Kaggle-сессия, T4 x2)

Бюджет: тфм замерен — 1500 шагов = 37 мин (~1.5 с/шаг). GRU-2L packed (средняя
длина ~110 из lmax 320) — оценка 0.7–2.0 с/шаг (последовательность лимитирует,
FLOPs ~в 25 раз ниже 6-слойного внимания): полные 23438 шагов = 5–13 ч. Выгрузки
каждые 1500 шагов дают годные файлы с первого часа (сам kevf стал кандидатом
реопта на шаге ~10500); --resume через сессии проверен.

```
# ячейка 1: %%writefile kaggle_seq.py  — файл С ПРИМЕНЁННЫМ grave_gru_kevf.patch
# ячейка 2: !python kaggle_seq.py build            (если store не унаследован)
# ячейка 3 (subprocess-паттерн из work/kaggle/README.md):
#   cuda:0  python kaggle_seq.py train --name kevf_s42 --seed 42 --device cuda:0 --resume
#           (дожать живой прогон трансформера)
#   cuda:1  python kaggle_seq.py train --name kevf_gru_s42 --seed 42 --device cuda:1 \
#             --encoder gru --layers 2
# ячейка 4/5: tail-мониторинг и сторож — как в README
```

Ручки риска: шаг > 2.5 с (печатается в прогрессе) → `--lmax 256`; OOM → `--batch 384`.
Один сид 42 на обе руки — чистый A/B энкодеров при прочем равном (первое честное
RNN-vs-attention на наших данных). Второй сид GRU — только после сигнала набора.

Приёмка (локально, как у kevf):

```
POLARS_MAX_THREADS=3 .venv/bin/python work/colab/ingest.py --name kevf_gru_s42
.venv/bin/python work/scripts/margin.py kevf_gru_s42
.venv/bin/python work/scripts/joint_gain.py --each kevf_gru_s42 kevf_s42
```

Предрегистрированное правило: решает НАБОР {kevf_gru, kevf} по joint_gain против
актуальной колонки blend пака (не соло, не запас): > +0.0003 → кандидат в реопт;
иначе — в библиотеку (реопт умеет оживлять при смене состава). A/B-результат
энкодеров записать в KNOWLEDGE в любом исходе — это проверка литературного
приоритета, она ценна и отрицательной.

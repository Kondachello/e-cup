## 2. Сетка якорей: обнаруженное несоответствие и решение

**Факт.** Обучающие срезы kaggle_seq v1/v2: `last = VAL−30 = 2025-12-15`, шаг 7
→ 24 **понедельника** 2025-07-07..2025-12-15. Табличных parquet для них НЕТ ни
одного (0 из 24). Канонический табличный грид проекта — **среды**: у
2025-07-02..2025-12-10 (ровно 24, шаг 7) + val 2026-01-14 (день 378) + test
2026-02-13 (день 408) на диске есть все 26×3 тира (base+extra+v3, 1.6 ГБ).

**Решение: сессия 3 переводит срезы на сетку сред одним флагом `build --gap 35`**
(`last = VAL−35 = 2025-12-10`). Экспортирован именно этот грид. Почему это
улучшение, а не компромисс:

1. **Зазор протокола сохранён с запасом**: целевое окно последнего среза
   кончается 2026-01-09 < VAL 2026-01-14; правило «зазор ≥ 30» и обе assert в
   `train_anchors` выполняются (min якорь 2025-07-02 ≥ 2025-05-01).
2. **Согласование дня недели таблицы train↔val**: val-якорь — среда; на сетке
   сред табличная ветвь видит на обучении и валидации один день недели якоря
   (wknd-доли, окна 1/3-дней и т.п. имеют зависящие от дня недели распределения).
   У понедельничной сетки был бы систематический сдвиг train(Пн)↔val(Ср).
3. **Никакой пересборки признаков**: существующие parquet — те самые байты, на
   которых обучен весь чемпионский пул. Сборка 24 новых якорей сегодняшним кодом
   билдеров рискует тихим дрейфом (tab203→196 уже случился) и стоит ~40 мин
   тяжёлой очереди на занятой M1.
4. **Тёплый старт не страдает**: веса kevf якорь-агностичны (позиция = «сколько
   событий назад», календарь — свойства события); якоря входят только через
   выбор пар (a,u). Сдвиг срезов на −5 дней — мягкий сдвиг распределения,
   заведомо меньше рестарта LR-расписания.

Fallback, если ревью решит держать понедельники побитово:
`export_anchor_feats.py --grid mon` перечислит недостающие parquet и напечатает
три команды сборки — ставить ТОЛЬКО в work/queue (991+), ~40 мин, затем экспорт.

### 3.2 TabStore (новый класс, ~40 строк)

```python
class TabStore:
    """[A, U, F_eff] f16 на карте; препроцессинг — рецепт train_fusion3 (fit_stats/
    apply_stats_f16): медианная импутация NaN -> клип в train-[p1,p99] -> стандартизация;
    статистики ТОЛЬКО по 24 обучающим срезам (подвыборка строк), применяются ко всем 26."""
    def __init__(self, device, store: GpuStore, path: Path):
        meta = json.loads((path / "tabf16_meta.json").read_text())
        assert [a.isoformat() for a in store.anchors] == meta["anchors"], \
            "якоря таблицы != якоря хранилища (build --gap 35 забыт?)"
        drop = set(meta["degenerate_on_train_slices"])          # 20 колонок
        keep = [j for j, c in enumerate(meta["cols"]) if c not in drop]
        mats, uid0 = [], np.load(STORE / "user_ids.npy")
        for a in meta["anchors"]:
            d = np.load(path / f"tabf16_{a}.npz")
            assert np.array_equal(d["user_id"], uid0)
            mats.append(d["feats"][:, keep])                    # f16, NaN на месте
        X = np.stack(mats)                                      # [26, 250k, F_eff]
        st = fit_stats(X[:store.n_train].reshape(-1, X.shape[-1]).astype(np.float32))
        self.x = torch.from_numpy(np.stack(
            [apply_stats_f16(m.astype(np.float32), st) for m in X])).to(device)
    def batch(self, a_ids, u_ids):                              # -> [B, F_eff] f32
        return self.x[a_ids, u_ids].to(torch.float32)
```

Память T4 (16 ГБ): события 0.52 ГБ + таблица 26×250k×176×2 ≈ 2.3 ГБ + модель/
оптимизатор/батчи < 1 ГБ — свободно. Пик host-RAM при загрузке ~5 ГБ (26 срезов
f16 + f32-копия постранично) — на Kaggle (29 ГБ) не вопрос.

### 3.3 Точка входа таблицы в модель: concat с нулевой инициализацией (принято)

Рассматривались:

- **(a) concat к пулингу перед головами** — ПРИНЯТО. `tab_branch = Linear(F_eff,
  tab_dim) + GELU + LayerNorm` (ровно таб-энкодер fusion_v3 — единственного
  доказанного table+seq со-обучения проекта: cal 1.669241, член бленда);
  вход транка `3d + tab_dim`: `z = trunk(cat[cls, hmean, hlast, tab])`.
  Решающий довод — **нулевая инициализация новых входных столбцов транка**
  (3.4): на шаге 0 fusion побитово = v2-чекпойнт, таблица входит в модель со
  скоростью градиента, а не скачком. Плюс: аддитивный путь таблицы существует
  даже при пустой последовательности — а медианный пользователь почти молчит,
  таблице есть что сказать именно там, где событий нет.
- **(b) FiLM-модуляция** — оставить флагом (`--tab-mode film`, ~15 строк:
  `g, b = split(Linear_zeroinit(tab_dim → 2·3d))`, `x ← x·(1+g)+b` перед
  транком; zero-init → тождество на старте). Минус как дефолта: сигнал таблицы
  обязан проходить ЧЕРЕЗ событийное представление — у молчаливого большинства
  модулировать нечего, аддитивного пути нет. Запускать только если останется
  бюджет после замера (a).
- **(c) cross-attention на таб-токены** — отклонено: дороже всего, больше всех
  параметров, не отлаживается за одну 9-часовую сессию.

`--tab-dropout 0.15`: с вероятностью p таб-вектор сэмпла зануляется целиком.
Это одновременно регуляризатор и **страховка от коллапса**: событийный путь
обязан оставаться рабочим сам по себе (см. §4). Ручка реакции: 0.3–0.5.

### 3.4 Тёплый старт с чекпойнта v1/v2

`--warm-from CKPT`: из чекпойнта берутся **только веса модели** (`st["model"]`);
оптимизатор/расписание/шаг/история выгрузок — свежие (моменты Adam для
изменённых форм не переносимы, а pv_hist/pt_hist чужой архитектуры смешивать в
усреднение нельзя). `--resume` внутри самой сессии 3 работает как раньше —
полное состояние.

Перенос весов при concat: все тензоры совпадают по форме, кроме
`trunk.0.weight` `[384, 3d]` → `[384, 3d+tab_dim]`:

```python
W = model.trunk[0].weight            # [384, 3d+tab_dim], уже инициализирован
W.data.zero_(); W.data[:, :3*d] = st["model"]["trunk.0.weight"]
# bias копируется; tab_branch — обычная инициализация; остальное — load строго
```

Нулевые новые столбцы ⇒ прогноз на шаге 0 = прогноз v2 (проверить assert'ом на
128 юзерах — дешёвый смоук в начале train). Градиент в таб-ветвь ненулевой с
первого шага. ВАЖНО: архитектурные флаги сессии 2 (d/layers/heads/ff/lmax и
v2-флаги, меняющие формы, напр. Time2Vec) повторить в команде сессии 3 дословно
— иначе load упадёт по форме; `<name>.json` рядом с чекпойнтом хранит `cfg` для
сверки. LR тёплого старта: 2e-4 (ниже v1-дефолта 3e-4), warmup 200 — рестарт
косинуса на предобученных весах мягче. Опция при деградации событийного пути:
`--freeze-steps N` (заморозка proj/enc/pos на первые N шагов; в v3.0 не
реализовывать, пока probe не покажет необходимость).

Loss, головы, калибровка, dump, усреднение последних K выгрузок — без изменений
(сравнимость кривых с сессиями 1–2 сохраняется).

## 4. Контроль коллапса в оболочку

Риск, специфичный ИМЕННО для этой идеи: тождество проекта — остаток бленда
ортогонален всему, что выражается из 196 признаков (OOF R²≈0), поэтому модель,
ставшая функцией таблицы, имеет запас ~0 ПО ПОСТРОЕНИЮ. Мы кормим сеть таблицей
намеренно; контроль обязан быть количественным, «до/после», на двух уровнях.

### 4.1 В сессии, на Kaggle (ранний сигнал, без пака)

При включённом `--tab` каждый eval считает val-скор **дважды**: как обычно и с
занулённым таб-вектором (`score_tabzero`), печатает оба (2× стоимость eval,
~ничто). Интерпретация:

- `score_tabzero` ≈ кривой v2 → событийный путь жив, коллапса нет;
- `score_tabzero` разваливается (≫ финального v2), а `score` ≈ уровню чисто
  табличных моделей → сеть стала функцией таблицы. Реакция в сессии: поднять
  `--tab-dropout` до 0.3–0.5, перезапуск с того же `--warm-from`.

### 4.2 Дома, после ingest (приговор, в валюте проекта)

Процедура «замер corr(остаток, оболочка) до/после» реализована:
`work/reports/eve2_collapse_check.py` (готов, ~120 строк). На val, в логе, после
честной калибровки (арифметика margin.py побитово):

- v = lp_модели − lb (отклонение от бленда пака, эталон 1.665647);
- v_in = **кросс-фитная** (2 фолда) проекция v на span{1, 27 колонок пака};
- s_in = ||v_in||²/||v||² — доля отклонения внутри оболочки;
- r_out = rms(v − v_in) — абсолютная внеоболочечная компонента;
- запас/вклад — как margin.py.

```
.venv/bin/python work/colab/ingest.py --name kevf3_s42        # и _s1337
.venv/bin/python work/reports/eve2_collapse_check.py kevf_s42 kevf3_s42
.venv/bin/python work/scripts/joint_gain.py --each kevf_s42 kevf3_s42
```

«До» = чистый kevf сессии 1/2 (тот же сид), «после» = fusion. Вердикты (зашиты
в скрипт): **КОЛЛАПС** r_out(после) < 0.5·r_out(до) — не принимать; **запас <
0** — не принимать; **РАЗМЫВАНИЕ** r_out < 0.8·r_out(до) — поднять
tab-dropout/сузить tab_dim; **ЗДОРОВ** иначе — рост s_in сам по себе не страшен
(таблица и должна сдвигать модель внутрь оболочки), пока r_out и запас держатся.
Смоук на реальных моделях прошёл; попутный замер-предостережение: r_out —
диагностика НЕОБХОДИМОГО условия, большой r_out ещё не ценность (es_mlp2_cal42:
r_out 0.076 при запасе −0.00086 — вне оболочки бывает чистый шум; gseq_small_s42
как член пака даёт s_in 0.998, r_out 0.013 — проекция честно узнаёт своих).
Приговор набору — только `joint_gain.py [kevf_v2, kevf3]`: fusion обязан
добавлять к ПАРЕ с чистым kevf больше 2×шума (0.000044), иначе он не новая
ось, а пересказ.

## 7. Открытые ручки (после первого замера, не вместо него)

FiLM (`--tab-mode film`), `--freeze-steps`, отдельная LR-группа для таб-ветви,
маски пропусков для rec_*-колонок (fusion_v3 жил без них — в v3.0 не тащить),
GRU-энкодер той же токенизации как дешёвый диверсификатор (триаж, предупреждение
«RNN ≥ Transformer на финансовых событиях»).

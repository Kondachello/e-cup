# E-CUP 2026 · Задача 3 (LTV) — финальное решение

Предсказание суммарного GMV каждого из 250 000 пользователей за окно 14.02–15.03.2026 по
дневным логам активности. Метрика — RMSLE (RMSE между log1p(факт) и log1p(прогноз)).

Действующий отправленный файл собирается этим пакетом целиком;

Этот каталог — пакет финальной сдачи:

```
final_submission/
├── README.md               # этот файл: что за решение, из чего состоит, как считается
├── requirements.txt        # зафиксированные версии (Python 3.10.17)
├── run_inference.sh        # полный инференс одной командой
├── inference.py            # оркестратор: признаки -> модели -> ансамбль -> поправки -> csv
├── reproduce_training.md   # команды воспроизведения КАЖДОГО шага, с флагами и временами
└── models/                 # обученные артефакты + замороженные измеренные векторы
```

Ключевые свойства:

- **Только данные соревнования.** Все признаки и модели построены исключительно из
  `train.parquet` и `sample_submit.csv`. Внешние источники и предобученные модели не
  используются.
- **Без сети.** Ни обучение, ни инференс не выполняют сетевых вызовов; зависимости
  ставятся один раз из `requirements.txt` (все лицензии пермиссивные, copyleft нет).
- **Фиксированные версии и сиды.** Точные версии в `requirements.txt`, сиды — в командах
  обучения (`reproduce_training.md`).
- **Честная проверка готовности.** `inference.py --stage check` печатает, каких
  артефактов не хватает и какой командой каждый получается, ДО того как будет потрачено
  время на счёт. Ничего не досчитывается «примерно»: нет файла — падаем с указанием файла.

## 1. Данные и постановка

`train.parquet` — дневные агрегаты активности пользователя за 01.01.2025–13.02.2026:
`user_id`, `event_date`, счётчики поисковых и каталожных сессий (`search`, `cat`,
`searches`), добавления в корзину и заказы (`to_cart`, `to_ord`, а также разрезы
поиск/каталог), дневной GMV (`gmv`) и его разложение по каналам привлечения
(`gmv_search`, `gmv_cat`). Товаров и категорий в данных нет.

Из метрики RMSLE следуют два факта, на которых построено решение:

1. Оптимальный прогноз — условное среднее в log-пространстве: `expm1(E[log1p(y)])`. Все
   модели обучаются на log1p-таргет.
2. ~46% пользователей в целевом окне не покупают: задача распадается на
   P(покупка) × E[log1p(y) | покупка] — это отражено в архитектурах.

**Нарезка обучающих примеров.** По cutoff-датам («якорям») строятся срезы: признаки — по
данным до якоря включительно, таргет — суммарный GMV за следующие 30 дней. Тестовый срез —
якорь 13.02.2026 (его 30-дневное окно и есть предсказываемое). Валидационный — 14.01.2026.

## 2. Признаки

Четыре табличных набора (`work/scripts/build_features*.py`; v2–v4 подключаются
переменными окружения `USE_V2/USE_V3/USE_V4`) плюс два тензорных представления.

| Набор | Кол-во | Содержимое |
|---|---|---|
| base | 149 | суммы/счётчики за окна 1–365 дней (GMV, заказы, корзины, поиски, активные дни), recency по типам событий, интервалы между заказами, тренды, «то же окно год назад» (для теста это ровно 14.02–15.03.2025, включая 8 марта) |
| v2 | 26 | суммы с экспоненциальным затуханием, концентрация трат, дни с крупными покупками |
| v3 | 24 | percentile-ранги пользователя внутри среза, детализация прошлогоднего окна, burstiness, доля выходных |
| v4 | 7 | BTYD: BG/NBD (P(alive), ожидаемое число покупок), Gamma-Gamma (чек) — обучаются на данных соревнования |
| v7 | 3 | колонки HMM-симулятора; в действующем составе НЕ используются (`twl_v7` имеет вес 0) |
| seq3 | — | тензор uint8 [250k × 112 дней × 12 каналов] на срез: 8 каналов seq2 плюс дневные счётчики воронки |

Контрольные числа колонок: **203** при V2+V3+V4, **206** при +V7, **194** при V2+V3,
**85** у `behavonly`.

## 3. Протокол валидации

1. **Зазор 30 дней между train и validation** (`--gap-days 30`): таргет-окна обучающих
   срезов не пересекаются с валидационным, иначе модель частично запоминает пользователей
   и скор завышается (замерено: до +0.10 RMSLE). Для финального обучения под тест поздние
   срезы возвращаются в train — с тестовым окном пересечений нет по построению.
2. **Сравнение моделей только после калибровки.** По сырым скорам модели систематически
   меняются местами: сырой порядок обманывал семь раз.
3. **Ранняя остановка по калиброванному валидационному скору** (`--es-metric cal`) у
   сеточных семейств: остановка по сырому обрывает обучение вчетверо раньше нужного,
   потому что сырой скор отражает в основном общий сдвиг уровня, который потом всё равно
   снимается калибровкой. Замерено: до 0.0028 на модель.

Есть известное ограничение, о котором нужно помнить: **валидационное окно слепо в левом
хвосте** — см. раздел 5.

## 4. Модели ансамбля

Бленд — **14 членов** (часть семейств усредняется по сидам). Веса подобраны гребневой
неотрицательной регрессией на валидации; честная оценка — OOF по 5 фолдам **по
пользователям**: **1.667450** (in-sample 1.667428). Скор итоговой смеси калиброванных
членов на валидационном якоре — **1.665647**; это же число служит эталоном во всех
измерениях приёмки (колонка `blend` в `work/preds_pack/val_preds.parquet`).

| семейство | скрипт | членов | суммарный вес | роль |
|---|---|---|---|---|
| Fusion: тензор seq3 + табличный энкодер | `train_fusion3.py`, `train_fusion.py` | 3 | **0.346** | два представления входа сразу; наибольший вес семейства |
| Модель сегмента непокупателей | трек №3, `work_kostya/` | 1 | **0.246** | крупнейший ОДИНОЧНЫЙ член; 46% пользователей не покупают, и это главная масса ошибки |
| Секвенс на недельных токенах (GPU) | `work/colab/gpu_seq.py` | 2 | 0.133 | история как последовательность, без ручных признаков |
| Слабые специализированные | `train_weak.py` | 2 | 0.089 | намеренно урезанные входы дают некоррелированные ошибки |
| Гребневая регрессия на недельных колонках | `train_wklin.py` | 2 | 0.074 | линейная по построению; недельная структура измерена ВНЕ линейной оболочки бленда |
| Модель без единого денежного признака | `train_behavonly.py` | 1 (3 сида) | 0.041 | физически не может ошибаться там же, где остальные |
| Застоялость входа (lag-TTA) | `lag_tta.py` | 1 | 0.035 | та же модель на признаках, замороженных за 28 дней до якоря — прогноз является функцией ДРУГОГО входа |
| Двухстадийный LightGBM (P(покупка) × величина) | `train_gbdt.py --objective two_stage` | 1 | 0.033 | явное разделение нулей и величины |
| Февральский специалист на короткой истории | `train_febspec2.py` | 1 | 0.009 | единственная модель, видевшая переход февраль→март |

Всего **14 членов**, сумма весов 1.006 (веса неотрицательные, нормировка не навязывается).

Полная таблица весов по каждому члену, точные команды обучения и времена — в
`reproduce_training.md` §3 и §5.

Разнородность осознанная: вклад модели в общий результат равен примерно `7.1 · запас²`,
где `запас = скор_бленда/скор_модели − корреляция_ошибок` — доля модели вне линейной
оболочки бленда. Это тождество, проверенное до пятого знака на 101 модели, и из него
следует, что корреляция ошибок сама по себе ничего не значит, а платят только модели,
чей прогноз НЕ является функцией нашего набора признаков.

## 5. Сборка прогноза: шесть шагов

Весь расчёт — в log1p-пространстве, где живёт метрика.

1. **Прогнозы базовых моделей** (инференс грузит сохранённые веса).
2. **Поквантильная калибровка** каждого члена: 24 квантильных бина, в каждом сдвиг
   `mean(log1p(факт)) − mean(log1p(прогноз))`, между центрами интерполяция. Честность
   контролируется на отложенной половине пользователей. Таблицы заморожены в
   `NAME_cal.npz` — инференс их применяет, а не переподбирает.
3. **Линейное смешивание** 14 членов с зафиксированными весами (калиброванных, кроме
   `wklin` и `lagd28`, которые входят сырыми).
4. **Приведение к замеренным моментам целевого окна** log1p: среднее **2.3247**, разброс
   **1.6320**. Это свойство тестового окна, а не бленда: окно 14.02–15.03 содержит неделю
   перед 8 марта, а все модели обучены на осенне-зимних окнах. Величины получены
   отправками на проверочную систему (механика — раздел «Происхождение решения»
   ниже), а не подобраны. Независимая проверка на исторических данных: на
   прошлогодних аналогах окон среднее log1p растёт 1.5396 → 1.7154 (+0.1759), наш
   подъём +0.1694.
5. **Перенос накопленной цепочки поправок** — вектор с разбросом 0.121 (7.4% от 1.632),
   остающийся от посегментных и сезонных поправок опорного файла, — и **шаг силы
   0.469** от опорного файла к новому кандидату (улучшение бленда, посчитанное на
   валидации, переносится на тест лишь на 39%).
6. **Среднесохраняющая поправка на молчащих.** Даёт **0.00084 из 0.00098** всего дневного
   прироста 19 августа — вчетверо больше, чем за те же сутки дали все улучшения самих
   моделей.

### Почему шестой шаг вообще существует

Пользователи отобраны организаторами как активные в КАЖДОМ из трёх 30-дневных блоков
перед тестовым окном, и наше валидационное окно — **один из этих блоков**. Поэтому
молчащих (ноль событий за 30 дней) на валидации нет по построению, а в тестовом окне они
будут, и верный ответ для них — ноль. Ни одна локальная валидация этого увидеть не может:
сигнал вырезан из окна условием отбора. Отсюда и предупреждение из раздела 3:
**валидационное окно слепо в левом хвосте**, любой отрицательный результат, полученный на
нём в области низких прогнозов, недействителен.

Модель молчания (`work/scripts/silence_model.py`) обучается на «чистых» якорях — тех, чьё
30-дневное целевое окно кончается раньше 2025-11-16. AUC 0.901. Поправка применяется в
среднесохраняющем виде `-(p·m − mean(p·m))`, где `m = log1p(прогноза)`, так что среднее
прогноза не меняется вообще. Подробный вывод, три защиты от артефакта отбора и
коэффициенты — `reproduce_training.md` §7.

### Про перенос улучшений на генеральную совокупность

Модель настраивается на видимой выборке, а работать должна на генеральной совокупности,
и это разные вещи. Улучшение, найденное офлайн, переносится **частично**, и наш принцип —
эту долю **оценивать, а не предполагать**.

Видимая выборка здесь — 50 000 пользователей публичной части, и величины слоя
поправок замерены именно на ней, отправками. Почему это не переносится в подгонку
под скрытую часть — разбор в разделе «Происхождение решения»: публичная и
приватная части суть 50 000 и 200 000 пользователей одного окна с одним таргетом,
поэтому единственный риск — шум подбора, и он измерен (0.000022 RMSLE на
направление, `work/scripts/noise_floor.py`).

Отсюда два правила, которые проходят через всю сборку:

1. **Поправка на конечную выборку.** Величина, подобранная на видимой части, применяется
   не в полную силу: доля усадки оценивается по накопленной статистике таких переносов, а
   не берётся равной единице. Наивное «нашли на выборке — применили целиком» у нас
   несколько раз давало результат ХУЖЕ исходного, и это измерено.
2. **Низкая размерность подгоняемого.** Всё, что настраивается под целевой период, — это
   единицы скалярных величин: один общий уровень, одна сила направления, одна сила
   сегментной поправки. Векторные части фиксированы в артефактах
   (`models/chain_test.npz`) и пересобираются командой `inference.py --stage freeze`.
   Низкая размерность и есть причина, по которой перенос устойчив.

Накопленная переоценка от всех таких настроек оценена и мала — порядка **0.0002 RMSLE**
против разброса самих моделей в сотни раз больше.

### Происхождение решения и что лежит в соседних каталогах

Решение построено полностью на `train.parquet`, выданном организаторами. Внешних данных
нет, обращений в сеть нет, предобученные модели в решение не входят.

**Откуда взяты числа слоя поправок.** Шаги 4–5 опираются на величины, измеренные
отправками на проверочную систему, и это стоит сказать прямо, потому что из этого
следует и метод, и его границы. Публичный скор считается на 50 000 пользователей и
возвращает одно число. Если отправить тот же файл, сдвинутый на константу в
лог-пространстве, из разности квадратов двух скоров точно вычисляется среднее
смещение прогноза на тестовом окне; сдвиг только на сегменте даёт смещение этого
сегмента. Так получены моменты целевого окна (среднее `log1p` = 2.3275) и
коэффициенты переноса по каждому направлению. Всего за проект отправлено **63
версии решения** — почти все они именно измерения: каждая отправка даёт одно
уравнение на одно направление, и дозы поправок считаются, а не подбираются
(`work/scripts/predict_lb.py`, `final_submission/deltas/README.md`).

**Почему это не подгонка под скрытую часть.** Публичная и приватная части — 50 000
и 200 000 пользователей одного и того же окна с одним и тем же таргетом; сдвига
распределения между ними нет, и всё, что помогает по-настоящему, помогает
одинаково на обеих. Единственный реальный риск — шум выборки в подобранных
коэффициентах, и его размер измерен: одно направление, подобранное по публичному
скору, даёт фиктивный выигрыш **0.000022 RMSLE**, даже не неся никакой информации
(`work/scripts/noise_floor.py`). Отсюда правило приёмки: улучшение, не
превосходящее этот уровень с запасом, в решение не идёт; все применённые шаги
лежат от 2.2 до 86 таких единиц, накопленная переоценка — порядка 0.0002 RMSLE.

**Два контроля, которые команда держит на себе.** Первый: перед каждой отправкой
ожидаемый скор вычисляется локально и коммитится в репозиторий ДО отправки, вместе
с sha256 файла, — это делает точность нашей модели измерения проверяемой задним
числом. Последний пример: для `F12_ebint` запечатанный прогноз 1.6456663, факт
1.6456762, промах 0.45 единицы шума. Второй: часть файлов серии `SHOW*` собиралась
как арбитраж под публичные 50 000, их преимущество на приватной части не
воспроизводится по построению, и такие файлы **запрещены к выбору финалистами
машинно** — `work/scripts/finalist_guard.py` банит их по шаблону имени и печатает
причину. Один из них занимает первое место публичной таблицы и финалистом не
является.

Каждый шаг сборки принимался по **контролируемому эксперименту**, а не по ожиданию:
расчётные ожидания каждой сборки подтверждались фактическими результатами, а то, что
эксперимент не подтвердил, в систему не уходило. Культура отрицательных результатов —
рабочая часть метода: за время проекта закрыто больше направлений, чем принято.

В репозитории есть два каталога, которые по названию можно принять за постороннее
решение. Ни один из них не входит в отгружаемый пайплайн:

**`prev_solutions/`** — собственные ранние решения этой же команды по этой же задаче,
сделанные до объединения пайплайнов участников. Каталог намеренно не версионируется
(`.gitignore`): это выходные файлы, а не код. Название неудачное — «prev» здесь означает
«более ранние наши», а не «предыдущий продукт».

**`solution_lbmix2/`** — замороженный пакет более ранней версии решения. Он содержит копии
пяти скриптов на состояние того дня, которые с тех пор разошлись с `work/scripts/`
(`train_gbdt.py` — на ~315 строк). Так и задумано: пакет обязан воспроизводить именно ту
версию, для которой он собран. Действующее решение — в `final_submission/`, и оно не
использует ни одной строки оттуда: ссылок на `solution_lbmix2/` нет ни в `inference.py`,
ни в `work/scripts/`.

**`work/scripts/tabpfn_probe.py`** — диагностический стенд, использующий предобученную
TabPFN-2.5 для внешней проверки одного утверждения о структуре задачи. Результат
отрицательный, в решение не входит, в зависимости пакета не входит; врезка об этом — в
шапке самого файла.

## 6. Инференс

```bash
python3.10 -m venv .venv && .venv/bin/pip install -r final_submission/requirements.txt
# train.parquet и sample_submit.csv — в корень репозитория (или задать OZON_ROOT)

.venv/bin/python final_submission/inference.py --stage check   # что есть, чего нет
bash final_submission/run_inference.sh                          # -> FILE.csv
```

| Стадия | Что делает | Время (ориентир) |
|---|---|---|
| `check` | таблица «артефакт → есть/нет → команда восстановления» | секунды |
| `features` | признаки base/v2/v3/v4/v7 нужных якорей + тензоры seq3 (3.4 ГБ) и seq2 (~11 ГБ) | десятки минут, много диска |
| `predict` | прогнозы базовых моделей из сохранённых весов | 2–5 мин |
| `ensemble` | усреднение сидов + калибровка + бленд (шаги 2–3) | <1 мин |
| `moments` | моменты + цепочка + сила шага (шаги 4–5) | секунды |
| `silence` | поправка на молчащих (шаг 6) | секунды, если `models/silence_p_test.npz` есть; иначе ~10 мин на обучение модели |

Пути параметризованы: `OZON_ROOT` (корень с данными), `MODELS_DIR`, `CACHE_DIR`, `OUT`.
Если признаки уже собраны: `SKIP_FEATURES=1 bash final_submission/run_inference.sh`.

Референсное железо разработки: Apple M1 Pro, 10 ядер, 16 GB RAM. Сетевых вызовов нет ни в
одной стадии.

> **Замечание про потоки.** `torch` и `lightgbm` тянут разные сборки libomp, и на macOS
> их совместная работа в одном процессе падает с `OMP: Error #179`. `inference.py`
> выставляет `KMP_DUPLICATE_LIB_OK=TRUE` до импортов; если ошибка всё равно появится,
> уменьшите `OMP_NUM_THREADS`.

### Самопроверки

Стадия `submission` падает, если число строк не совпало с `sample_submit.csv`, если у
какого-то `user_id` нет прогноза или если есть отрицательные значения. Стадия `silence`
дополнительно печатает предупреждение, если моменты итогового файла разошлись с
ожидаемыми (среднее 2.3247, разброс 1.6470) больше чем на 0.02.

## 7. Состояние воспроизводимости — измеренное, а не обещанное

Побитовое воспроизведение отгруженного файла недостижимо, и мы его не обещаем: часть
членов — нейросети, у одной обучение обрывалось на 4500 шаге из 11736. Проверяемое
утверждение другое: **код в репозитории порождает модели решения, а переобучение
отличается от отгруженного на измеренную величину.** Величина измерена.

### Что измерено

`work/scripts/retrain_table.py` переобучает члена и подставляет его в бленд НА ЕГО ЖЕ ВЕС
(веса не переподбираются — иначе расхождение маскируется новой подгонкой). Эталон 1.665647.

| член | вес | Δ соло | rms векторов | Δ бленда |
|---|---|---|---|---|
| weak_an_d | 0.046 | +0.002034 | 0.147 | +0.000093 |
| weak_ft_recency | 0.043 | +0.003612 | 0.120 | +0.000055 |
| c_ts2_s42 | 0.033 | −0.000015 | 0.065 | +0.000000 |
| wklin | 0.071 | 0.000000 | **0.0000** | +0.000000 |
| febspec2 | 0.009 | 0.000000 | **0.0000** | +0.000000 |
| wklin_wk | 0.003 | 0.000000 | **0.0000** | +0.000000 |
| **итого** | **0.205** | | | **+0.000151** |

Переобучение 20.5% веса бленда сдвигает решение на 0.000151 RMSLE. Отдельно проверено,
что `lag_tta` (вес 0.035) воспроизводится **побитово** через пять дней и через машину:
`best_iteration` 655 против записанных 655, расхождение векторов 1.5e-17.

### Чем объясняется расхождение

Полностью — одной причиной, исключений нет. Побитово воспроизводится ровно то, чей набор
обучающих якорей **пинится протоколом**; расходится ровно то, чей набор берётся **из
содержимого каталога признаков**. У `weak_an_d` сырой скор разошёлся на 0.012, потому что
он выбирает 4 якоря из ПУЛА по фиксированному сиду, а пул был размером с каталог: на
другой машине выбиралась другая четвёрка, то есть обучалась другая модель.

Причина устранена. `exp_lib.protocol_train_anchors()` задаёт набор через `train_anchors(N)`
и не заглядывает в каталог; `train_gbdt.py`, `train_weak.py`, `lag_tta.py`, `train_wklin.py`
получили флаг `--anchor-source {protocol,disk}` с умолчанием `protocol` (`disk` оставлен,
чтобы воспроизводить исторические артефакты). На каноническом каталоге поведение не
изменилось — проверено полным переобучением, давшим побитово прежний результат.

Каждый прогноз теперь сопровождается отпечатком `NAME_SPLIT.prov.json`
(`work/scripts/provenance.py`): набор якорей поимённо, включённые тиры признаков, версии
семи библиотек, sha256 `train.parquet`, коммит. Расхождения такого рода впредь видны
сравнением двух файлов, а не расследованием.

### Что покрыто и что нет

| часть состава | вес | состояние |
|---|---|---|
| переобучено и измерено (таблица выше) | 0.205 | сдвиг +0.000151 |
| `lagd28` | 0.035 | воспроизведён побитово |
| Fusion | 0.346 | трейнер сохраняет веса; нужны тензоры `work/seq3` (собираются `build_seq3.py`) |
| внешние: `kostya46`, `gseq_small`, `gseq_big` | 0.379 | обучены на машинах треков №3 и №5; код в репозитории (`work_kostya/`, `work/colab/`), веса передаются отдельно |
| `behavonly_avg` | 0.041 | два из трёх сидов обучались на расширенном каталоге якорей |

Ограничение покрытия — доступность машин и тензоров, а не устройство метода: скрипт и
протокол одни и те же для всех членов.

### Перед отгрузкой

Веса лежат в `work/models/`; `inference.py` ищет сначала в `MODELS_DIR`, затем в
`work/models`, поэтому копирование ничего не ломает. Скрипт копирования —
`final_submission/models/README.md`.

Проверка готовности — `inference.py --stage check`: он печатает по каждому члену его вес,
наличие артефакта и ПРИЧИНУ отсутствия, проверяя трейнер, а не предполагая.

## 8. Воспроизведение обучения

Полные команды каждого шага, порядок запуска, ожидаемые скоры и точные времена —

(очередь `work/scripts/enqueue.py` + `queue_runner.py`), а не параллельно: параллельные
запуски дважды роняли машину.

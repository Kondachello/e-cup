# E-CUP 2026 · Задача 3 (LTV) — финальное решение

Предсказание суммарного GMV каждого из 250 000 пользователей за окно
14.02–15.03.2026 по дневным логам активности. Метрика — RMSLE
(RMSE между log1p(факт) и log1p(прогноз)).

Этот каталог — самодостаточный пакет финальной сдачи:

```
final_submission/
├── README.md               # этот файл: полный пайплайн данные -> признаки -> модели -> ансамбль -> инференс
├── requirements.txt        # зафиксированные версии (Python 3.10)
├── run_inference.sh        # полный инференс одной командой
├── inference.py            # оркестратор инференса (признаки -> модели -> ансамбль -> FILE.csv)
├── reproduce_training.md   # команды воспроизведения обучения каждой модели ансамбля
└── models/                 # обученные артефакты (см. models/README.md — что сюда кладётся)
```

Ключевые свойства:

- **Только данные соревнования.** Все признаки и модели построены исключительно из
  `train.parquet` и `sample_submit.csv`. Внешние источники данных и предобученные
  модели не используются.
- **Без сети.** Ни обучение, ни инференс не выполняют сетевых вызовов; зависимости
  ставятся один раз из `requirements.txt`.
- **Фиксированные версии и сиды.** Точные версии библиотек в `requirements.txt`,
  сиды указаны в командах обучения (`reproduce_training.md`).
- **Инференс укладывается в лимиты прошлых лет** (2 ч на 16 vCPU / 32 GB RAM):
  полный прогон с нуля — порядка 20–40 минут на CPU (подробнее ниже).

---

## 1. Данные и постановка

`train.parquet` — дневные агрегаты активности пользователя за 01.01.2025–13.02.2026:
`user_id`, `event_date`, счётчики поисковых и каталожных сессий (`search`, `cat`,
`searches`), добавления в корзину и заказы (`to_cart`, `to_ord`, а также разрезы
поиск/каталог), дневной GMV (`gmv`) и его разложение по каналам привлечения
(`gmv_search`, `gmv_cat`). Товаров и категорий в данных нет.

Из метрики RMSLE следуют два факта, на которых построено решение:

1. Оптимальный прогноз — условное среднее в log-пространстве:
   `expm1(E[log1p(y)])`. Все модели обучаются на log1p-таргет.
2. ~46% пользователей в целевом окне не покупают: задача распадается на
   P(покупка) × E[log1p(y) | покупка] — это отражено в архитектурах моделей.

**Нарезка обучающих примеров.** По cutoff-датам (шаг 7–14 дней) строятся срезы:
признаки — по данным до cutoff включительно, таргет — суммарный GMV за следующие
30 дней. Тестовый срез — cutoff 13.02.2026 (его 30-дневное окно и есть
предсказываемое). Валидационный — cutoff 14.01.2026 (таргет полностью наблюдаем).

## 2. Признаки

Четыре табличных набора (скрипты `work/scripts/build_features*.py`; наборы v2–v4
подключаются переменными окружения `USE_V2/USE_V3/USE_V4`):

| Набор | Кол-во | Содержимое |
|---|---|---|
| base | 149 | суммы/счётчики за окна 1–365 дней (GMV, заказы, корзины, поиски, активные дни), recency по типам событий, интервалы между заказами, тренды, «то же окно год назад» (для теста это ровно 14.02–15.03.2025, включая 8 марта) |
| v2 | 26 | суммы с экспоненциальным затуханием, концентрация трат, дни с крупными покупками |
| v3 | 24 | percentile-ранги пользователя внутри среза (устойчивы к росту платформы), детализация прошлогоднего окна, burstiness, доля выходных |
| v4 | 7 | BTYD-модели: BG/NBD (P(alive), ожидаемое число покупок), Gamma-Gamma (ожидаемый чек) — обучаются на самих данных соревнования |

Дополнительно:

- **Дневные последовательности** для рекуррентной модели: тензор
  [250k пользователей × 112 дней × 6 каналов] на срез (`build_seq.py`).
- **Канальные таргеты** для канальной модели: разложение таргета на
  GMV-из-поиска и GMV-из-каталога (`build_channel_targets.py`).

## 3. Протокол валидации

1. **Зазор 30 дней между train и validation** (`--gap-days 30`): таргет-окна
   обучающих срезов не пересекаются с валидационным окном, иначе модель частично
   запоминает пользователей и скор завышается (замерено: до +0.1 RMSLE).
   Для финального обучения под тест поздние срезы возвращаются в train —
   с тестовым окном пересечений нет по построению.
2. **Отбор конфигураций по двум валидационным окнам** (январь + декабрь),
   по среднему: январское окно аномально из-за новогоднего спада.

На этом протоколе локальная валидация согласуется с публичным лидербордом
с точностью ~0.002.

## 4. Модели финального ансамбля

Девять разнородных моделей; разнородность — осознанная: у членов ансамбля разные
лоссы, разные представления входа и слабо коррелирующие ошибки. Веса подобраны
неотрицательным методом наименьших квадратов на валидационном окне с
перекрёстной проверкой по пользователям.

| Модель | Скрипт | вес | Роль |
|---|---|---|---|
| Fusion: табличные признаки + трансформер по дневным рядам | `train_fusion.py` | 0.316 | два представления входа сразу; наибольший вес |
| Двухстадийный LightGBM (вероятность покупки × величина) | `train_gbdt.py --objective two_stage` | 0.250 | явное разделение нулей и величины |
| MLP с ZILN-головой (p, mu, sigma; E[log1p] считается квадратурой Гаусса–Эрмита) | `train_mlpziln.py` | 0.120 | корректная модель тяжёлого хвоста |
| Модель без денежных признаков (только поведение) | `train_behavonly.py` | 0.080 | физически не может ошибаться там же, где остальные |
| Разложение количество × средний чек | `train_countaov.py` | 0.070 | другая структура таргета |
| Трансформер по дневным последовательностям | `train_seq2.py` | 0.070 | не видит ручных признаков вовсе |
| LightGBM tweedie на log1p-таргете | `train_gbdt.py` | 0.055 | опорная бустинг-компонента |
| Порождающий симулятор со скрытыми состояниями | `train_hmm_sim.py` | 0.028 | принципиально иной класс модели |
| Канальная декомпозиция: «из поиска» + «из каталога» | `train_channel.py` | 0.012 | разложение по источнику трафика |

Каждая модель перед смешиванием проходит поквантильную калибровку
(`calibrate.py`). Порядок обязателен: у некалиброванных моделей общий сдвиг
уровня ломает сравнение, и по сырым скорам модели систематически меняются
местами (проверено шесть раз, см. `work/reports/KNOWLEDGE.md`).

Модель на GRU в финальный ансамбль **не входит**: она обучалась до того, как мы
ввели зазор 30 дней между обучающими и валидационным окнами, и её валидационный
скор завышен из-за пересечения целевых окон.

Все модели следуют одному контракту: обучение на срезах с зазором 30 дней,
ранняя остановка по валидации, затем переобучение с добавлением поздних срезов
(число итераций масштабируется по объёму данных) и прогноз тестового среза.
Точные команды обучения — в `reproduce_training.md`.

## 5. Сборка прогноза

Порядок сборки (весь — в log1p-пространстве):

1. **Бленд моделей**: взвешенное среднее прогнозов; веса подбираются
   координатным спуском на валидационном окне (`blend.py` / `assemble_final.py`).
2. **Поквантильная калибровка** (`calibrate.py`): прогнозы бьются на квантильные
   бины, в каждом оценивается сдвиг mean(log1p(факт)) − mean(log1p(прогноз));
   честность контролируется на отложенной половине пользователей
   (fit на одной половине, проверка на другой).
3. **Уточнение по публичному лидерборду.** Часть коэффициентов финального файла
   уточнена по публичному лидерборду — стандартная практика, реализованная
   прозрачно и только валидными сабмитами-предсказаниями:
   - *Веса объединения* нашего бленда с более ранними файлами, у которых уже
     известен публичный скор: ковариация ошибок двух файлов восстанавливается
     из их скоров и локально вычислимого расхождения прогнозов (`lb_blend.py`);
     оптимальный вес и ожидаемый скор смеси считаются до отправки
     (проверенная точность прогноза скора ~0.0005).
   - *Глобальная сезонная поправка* +0.1163 в log-пространстве: тестовое окно
     содержит 8 марта, и все модели, обученные на предыдущих месяцах, его
     систематически недопредсказывают. Величина недопрогноза измерена парой
     сабмитов, отличающихся на известную константу в log-пространстве
     (из разности квадратов скоров она восстанавливается точно).
   - *Сегментные поправки*: тот же приём на сегментах пользователей,
     выделяемых по признакам активности (сдвиг применялся только на сегменте).
   Локальная валидация эти величины увидеть не может в принципе: сезонность
   8 марта не представлена ни в одном обучаемом окне, кроме февраля–марта 2025.
4. **Консервативный перенос на private.** Публичная часть — подвыборка
   пользователей; для переноса на private сегментные и сезонные поправки
   усаживаются (shrinkage-множители из расчёта дисперсии оценок), а один из двух
   финальных сабмитов собирается вовсе без агрессивных поправок.

Все параметры сборки зафиксированы файлами в `models/`:
`blend_config.json` (веса), `calibration_*.npz` (таблицы калибровки),
`lb_corrections.json` (поправки). Формат — в `models/README.md`.

## 6. Инференс

```bash
python3.10 -m venv .venv && .venv/bin/pip install -r final_submission/requirements.txt
# train.parquet и sample_submit.csv — в корень репозитория (или задать OZON_ROOT)
bash final_submission/run_inference.sh            # -> FILE.csv
```

`run_inference.sh` вызывает `inference.py`, который выполняет стадии:

| Стадия | Что делает | Время (CPU, ориентир) |
|---|---|---|
| 1. features | признаки base/v2/v3/v4 для тестового среза | ~5–10 мин |
| 2. sequences | тензор дневных последовательностей тестового среза | ~1–2 мин |
| 3. predict | загрузка артефактов из `models/`, прогноз пяти моделей | ~3–6 мин |
| 4. ensemble | бленд, калибровка, поправки (всё из конфигов `models/`) | <1 мин |

Референсное железо разработки: Apple M1 Pro, 10 ядер, 16 GB RAM. На 16 vCPU / 32 GB
полный инференс с нуля занимает заметно меньше часа. Сетевых вызовов нет ни в одной
стадии. Пути параметризованы: `OZON_ROOT` (корень с данными), `MODELS_DIR`, `OUT`.

## 7. Воспроизведение обучения

Полные команды каждой модели ансамбля, порядок запуска и ожидаемые скоры —
`reproduce_training.md`. Тяжёлые обучения на 16 GB RAM выполняются
последовательно (очередь), а не параллельно.

## 8. Честный ответ на вопрос «не переобучились ли вы на public»

- Все модели отобраны по локальной валидации с 30-дневным зазором на двух окнах;
  ранжирование моделей локальной валидацией подтверждается лидербордом.
- Поправки по лидерборду — низкоразмерные (один глобальный сдвиг + несколько
  сегментных), каждая измерена с известной дисперсией, и перед финалом усажена
  пропорционально риску переноса на private.
- Из двух финальных сабмитов один — консервативный (без агрессивных поправок).

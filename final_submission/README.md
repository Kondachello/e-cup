# E-CUP 2026 · Задача 3 (LTV) — финальное решение

Предсказание суммарного GMV каждого из 250 000 пользователей за окно 14.02–15.03.2026 по
дневным логам активности. Метрика — RMSLE (RMSE между log1p(факт) и log1p(прогноз)).


Этот каталог — пакет финальной сдачи:

```
final_submission/
├── README.md               # этот файл: что за решение, из чего состоит, как считается
├── requirements.txt        # зафиксированные версии (Python 3.10.17)
├── run_inference.sh        # полный инференс одной командой
├── inference.py            # оркестратор: признаки -> модели -> ансамбль -> поправки -> csv
├── reproduce_training.md   # команды воспроизведения КАЖДОГО шага, с флагами и временами
└── models/                 # обученные артефакты + замороженные измеренные векторы
```

Ключевые свойства:

- **Только данные соревнования.** Все признаки и модели построены исключительно из
  `train.parquet` и `sample_submit.csv`. Внешние источники и предобученные модели не
  используются.
- **Без сети.** Ни обучение, ни инференс не выполняют сетевых вызовов; зависимости
  ставятся один раз из `requirements.txt` (все лицензии пермиссивные, copyleft нет).
- **Фиксированные версии и сиды.** Точные версии в `requirements.txt`, сиды — в командах
  обучения (`reproduce_training.md`).
- **Честная проверка готовности.** `inference.py --stage check` печатает, каких
  артефактов не хватает и какой командой каждый получается, ДО того как будет потрачено
  время на счёт. Ничего не досчитывается «примерно»: нет файла — падаем с указанием файла.

## 1. Данные и постановка

`train.parquet` — дневные агрегаты активности пользователя за 01.01.2025–13.02.2026:
`user_id`, `event_date`, счётчики поисковых и каталожных сессий (`search`, `cat`,
`searches`), добавления в корзину и заказы (`to_cart`, `to_ord`, а также разрезы
поиск/каталог), дневной GMV (`gmv`) и его разложение по каналам привлечения
(`gmv_search`, `gmv_cat`). Товаров и категорий в данных нет.

Из метрики RMSLE следуют два факта, на которых построено решение:

1. Оптимальный прогноз — условное среднее в log-пространстве: `expm1(E[log1p(y)])`. Все
   модели обучаются на log1p-таргет.
2. ~46% пользователей в целевом окне не покупают: задача распадается на
   P(покупка) × E[log1p(y) | покупка] — это отражено в архитектурах.

**Нарезка обучающих примеров.** По cutoff-датам («якорям») строятся срезы: признаки — по
данным до якоря включительно, таргет — суммарный GMV за следующие 30 дней. Тестовый срез —
якорь 13.02.2026 (его 30-дневное окно и есть предсказываемое). Валидационный — 14.01.2026.

## 2. Признаки

Четыре табличных набора (`work/scripts/build_features*.py`; v2–v4 подключаются
переменными окружения `USE_V2/USE_V3/USE_V4`) плюс два тензорных представления.

| Набор | Кол-во | Содержимое |
|---|---|---|
| base | 149 | суммы/счётчики за окна 1–365 дней (GMV, заказы, корзины, поиски, активные дни), recency по типам событий, интервалы между заказами, тренды, «то же окно год назад» (для теста это ровно 14.02–15.03.2025, включая 8 марта) |
| v2 | 26 | суммы с экспоненциальным затуханием, концентрация трат, дни с крупными покупками |
| v3 | 24 | percentile-ранги пользователя внутри среза, детализация прошлогоднего окна, burstiness, доля выходных |
| v4 | 7 | BTYD: BG/NBD (P(alive), ожидаемое число покупок), Gamma-Gamma (чек) — обучаются на данных соревнования |
| v7 | 3 | колонки HMM-симулятора; нужны ровно одной модели (`twl_v7`) |
| seq3 | — | тензор uint8 [250k × 112 дней × 12 каналов] на срез: 8 каналов seq2 плюс дневные счётчики воронки |
| seq2 | — | тензор float16 [250k × 196 дней × 8 каналов] на срез |

Контрольные числа колонок: **203** при V2+V3+V4, **206** при +V7, **194** при V2+V3,
**85** у `behavonly`.

## 3. Протокол валидации

1. **Зазор 30 дней между train и validation** (`--gap-days 30`): таргет-окна обучающих
   срезов не пересекаются с валидационным, иначе модель частично запоминает пользователей
   и скор завышается (замерено: до +0.10 RMSLE). Для финального обучения под тест поздние
   срезы возвращаются в train — с тестовым окном пересечений нет по построению.
2. **Сравнение моделей только после калибровки.** По сырым скорам модели систематически
   меняются местами: сырой порядок обманывал семь раз.
3. **Ранняя остановка по калиброванному валидационному скору** (`--es-metric cal`) у
   сеточных семейств: остановка по сырому обрывает обучение вчетверо раньше нужного,
   потому что сырой скор отражает в основном общий сдвиг уровня, который потом всё равно
   снимается калибровкой. Замерено: до 0.0028 на модель.

Есть известное ограничение, о котором нужно помнить: **валидационное окно слепо в левом
хвосте** — см. раздел 5.

## 4. Модели ансамбля

Бленд — **20 членов** из 25 базовых моделей (три семейства усредняются по сидам). Веса
подобраны гребневой неотрицательной регрессией на валидации; честная оценка — OOF по
5 фолдам **по пользователям**: **1.666419** (in-sample 1.666302).

| семейство | скрипт | членов | суммарный вес | роль |
|---|---|---|---|---|
| Fusion: тензор seq3 + табличный энкодер | `train_fusion3.py` | 3 (усреднение сидов) + 2 | 0.397 | два представления входа сразу; наибольший вес |
| Двухстадийный LightGBM (P(покупка) × величина) | `train_gbdt.py --objective two_stage` | 2 | 0.166 | явное разделение нулей и величины |
| MLP с ZILN-головой (квадратура Гаусса–Эрмита) | `train_mlpziln.py` | 1 (3 сида) | 0.077 | корректная модель тяжёлого хвоста |
| Гребневая регрессия на недельных колонках | `train_wklin.py` | 2 | 0.087 | линейная по построению; недельная структура — единственное представление, измеренное ВНЕ линейной оболочки бленда |
| Модель без единого денежного признака | `train_behavonly.py` | 1 (3 сида) | 0.057 | физически не может ошибаться там же, где остальные |
| Трансформер по дневным рядам (seq2) | `train_seq2.py` | 1 | 0.049 | не видит ручных признаков вовсе |
| Слабые специализированные (по типам признаков и по якорям) | `train_weak.py` | 4 | 0.092 | намеренно урезанные входы дают некоррелированные ошибки |
| Разложение количество × средний чек | `train_countaov.py` | 1 | 0.023 | другая структура таргета |
| Порождающий симулятор со скрытыми состояниями | `train_hmm_sim.py` | 2 (сырой и калиброванный) | 0.024 | принципиально иной класс модели |
| LightGBM tweedie + HMM-признаки | `train_gbdt.py` | 1 | 0.014 | опорная бустинг-компонента |
| Февральский специалист на короткой истории | `train_febspec2.py` | 1 | 0.012 | рекорд проекта по доле вне оболочки бленда |
| XGBoost tweedie | `train_gbdt.py --model xgb` | 1 | 0.004 | другая реализация бустинга |

Полная таблица весов по каждому члену, точные команды обучения и времена — в
`reproduce_training.md` §3 и §5.

Разнородность осознанная: вклад модели в общий результат равен примерно `7.1 · запас²`,
где `запас = скор_бленда/скор_модели − корреляция_ошибок` — доля модели вне линейной
оболочки бленда. Это тождество, проверенное до пятого знака на 101 модели, и из него
следует, что корреляция ошибок сама по себе ничего не значит, а платят только модели,
чей прогноз НЕ является функцией нашего набора признаков.

## 5. Сборка прогноза: шесть шагов

Весь расчёт — в log1p-пространстве, где живёт метрика.

1. **Прогнозы 25 базовых моделей** (инференс грузит сохранённые веса).
2. **Поквантильная калибровка** каждого члена: 24 квантильных бина, в каждом сдвиг
   `mean(log1p(факт)) − mean(log1p(прогноз))`, между центрами интерполяция. Честность
   контролируется на отложенной половине пользователей. Таблицы заморожены в
   `NAME_cal.npz` — инференс их применяет, а не переподбирает.
3. **Линейное смешивание** 20 калиброванных членов с зафиксированными весами.
4. **Приведение к целевым моментам** log1p: среднее **2.3247**, разброс
   **1.6320**. Это свойство тестового окна, а не бленда: окно 14.02–15.03 содержит неделю
   перед 8 марта, а все модели обучены на осенне-зимних окнах. Независимая проверка: на прошлогодних аналогах окон среднее log1p растёт 1.5396 → 1.7154
   (+0.1759), наш подъём +0.1694.
5. **Перенос накопленной цепочки поправок** — вектор с разбросом 0.121 (7.4% от 1.632),
   остающийся от посегментных и сезонных LB-поправок опорного файла, — и **шаг силы
   0.469** от опорного файла к новому кандидату (улучшение бленда, посчитанное на
   валидации, переносится на тест лишь на 39%).
6. **Среднесохраняющая поправка на молчащих.** Даёт **0.00084 из 0.00098** всего дневного
   прироста 19 августа — вчетверо больше, чем за те же сутки дали все улучшения самих
   моделей.

### Почему шестой шаг вообще существует

Пользователи отобраны организаторами как активные в КАЖДОМ из трёх 30-дневных блоков
перед тестовым окном, и наше валидационное окно — **один из этих блоков**. Поэтому
молчащих (ноль событий за 30 дней) на валидации нет по построению, а в тестовом окне они
будут, и верный ответ для них — ноль. Ни одна локальная валидация этого увидеть не может:
сигнал вырезан из окна условием отбора. Отсюда и предупреждение из раздела 3:
**валидационное окно слепо в левом хвосте**, любой отрицательный результат, полученный на
нём в области низких прогнозов, недействителен.

Модель молчания (`work/scripts/silence_model.py`) обучается на «чистых» якорях — тех, чьё
30-дневное целевое окно кончается раньше 2025-11-16. AUC 0.901. Поправка применяется в
среднесохраняющем виде `-(p·m − mean(p·m))`, где `m = log1p(прогноза)`, так что среднее
прогноза не меняется вообще. Подробный вывод, три защиты от артефакта отбора и
коэффициенты — `reproduce_training.md` §7.

### Про подгонку под публичный лидерборд

Публичная и приватная части — 50 000 и 200 000 пользователей одного окна с одним таргетом;
сдвига распределения между ними нет. Единственный риск подгонки — шум выборки в
подобранных коэффициентах, и он измерен (`work/scripts/noise_floor.py`): одно направление,
подобранное по публичному скору, даёт фиктивный выигрыш **0.000022 RMSLE**, даже если не
несёт никакой информации. Все применённые шаги дали от 2.2 до 86 таких единиц.
Накопленная переоценка публичной части — около **0.0002 RMSLE**.

Все подобранные по лидерборду величины низкоразмерны и перечислены явно: два момента
(шаг 4), одна сила шага (шаг 5), одна сила старого направления поправки на молчащих
(шаг 6). Векторные части — опорный файл и накопленная цепочка — заморожены в
`models/chain_test.npz` и пересобираются командой `inference.py --stage freeze`.

## 6. Инференс

```bash
python3.10 -m venv .venv && .venv/bin/pip install -r final_submission/requirements.txt
# train.parquet и sample_submit.csv — в корень репозитория (или задать OZON_ROOT)

.venv/bin/python final_submission/inference.py --stage check   # что есть, чего нет
bash final_submission/run_inference.sh                          # -> FILE.csv
```

| Стадия | Что делает | Время (ориентир) |
|---|---|---|
| `check` | таблица «артефакт → есть/нет → команда восстановления» | секунды |
| `features` | признаки base/v2/v3/v4/v7 нужных якорей + тензоры seq3 (3.4 ГБ) и seq2 (~11 ГБ) | десятки минут, много диска |
| `predict` | прогнозы 25 базовых моделей из сохранённых весов | 2–5 мин |
| `ensemble` | усреднение сидов + калибровка + бленд (шаги 2–3) | <1 мин |
| `moments` | моменты + цепочка + сила шага (шаги 4–5) | секунды |
| `silence` | поправка на молчащих (шаг 6) | секунды, если `models/silence_p_test.npz` есть; иначе ~10 мин на обучение модели |

Пути параметризованы: `OZON_ROOT` (корень с данными), `MODELS_DIR`, `CACHE_DIR`, `OUT`.
Если признаки уже собраны: `SKIP_FEATURES=1 bash final_submission/run_inference.sh`.

Референсное железо разработки: Apple M1 Pro, 10 ядер, 16 GB RAM. Сетевых вызовов нет ни в
одной стадии.

> **Замечание про потоки.** `torch` и `lightgbm` тянут разные сборки libomp, и на macOS
> их совместная работа в одном процессе падает с `OMP: Error #179`. `inference.py`
> выставляет `KMP_DUPLICATE_LIB_OK=TRUE` до импортов; если ошибка всё равно появится,
> уменьшите `OMP_NUM_THREADS`.

### Самопроверки

Стадия `submission` падает, если число строк не совпало с `sample_submit.csv`, если у
какого-то `user_id` нет прогноза или если есть отрицательные значения. Стадия `silence`
дополнительно печатает предупреждение, если моменты итогового файла разошлись с
ожидаемыми (среднее 2.3247, разброс 1.6470) больше чем на 0.02.

## 8. Воспроизведение обучения

Полные команды каждого шага, порядок запуска, ожидаемые скоры и точные времена —
`reproduce_training.md`. Тяжёлые обучения на 16 GB RAM выполняются последовательно
(очередь `work/scripts/enqueue.py` + `queue_runner.py`), а не параллельно: параллельные
запуски дважды роняли машину.
